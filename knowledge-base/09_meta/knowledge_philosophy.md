# 知识库哲学

## 核心理念

知识库不是资料仓库，而是"能逼你产出判断、复盘和决策"的系统。

### 为什么不是资料仓库

**资料仓库的问题**：
- 堆积大量摘抄和笔记
- 缺乏结构和组织
- 难以检索和复用
- 不产生新的理解

**我们要的是**：
- 强制思考和判断
- 记录决策过程
- 沉淀可复用的方法
- 形成个人研究操作系统

## 四类输出

### 1. 快速进入新课题
**场景**：接触新的研究方向
**需要**：
- 领域全景图（Knowledge Map）
- 核心问题树
- 关键论文节点
- 主要流派和方法

**不需要**：
- 完整的论文列表
- 详尽的历史回顾

### 2. 深化基础理解
**场景**：打透核心概念
**需要**：
- 多视角的理解（Concept Note）
- 物理图像和数学表述
- 常见误解和困惑点
- 费曼式简化讲解

**不需要**：
- 教科书式的定义摘抄
- 纯数学推导

### 3. 沉淀研究主线
**场景**：项目复盘和经验积累
**需要**：
- 关键决策记录（Decision）
- 失败尝试和教训
- 方法演化过程
- 可复用的判断框架

**不需要**：
- 日常进展流水账
- 技术细节堆砌

### 4. 形成方法库
**场景**：遇到类似问题时快速调用
**需要**：
- 方法的适用场景（Method Note）
- 常见陷阱和判断标准
- 实际使用经验
- 代码和工具链接

**不需要**：
- 理论推导
- 完整的教程

## 设计原则

### 1. 最小单元是"问题"

**不要**：创建"CKM 矩阵"这样的大主题
**而是**：
- "为什么 CKM 矩阵是酉矩阵？"
- "如何从实验测量约束 CKM 矩阵？"
- "CKM 矩阵的相位如何导致 CP 破坏？"

**原因**：
- 问题导向强制思考
- 便于检索和复用
- 避免知识堆积

### 2. 记录判断和决策

**不要**：只记录"用了 sPlot"
**而是**：
- 为什么选 sPlot 而不是 Fit？
- 当时的信息约束是什么？
- 实际效果如何？
- 如果重来会怎么做？

**原因**：
- 判断力是核心竞争力
- 决策过程可复用
- 失败经验同样宝贵

### 3. 使用统一模板

**不要**：自由发挥的笔记格式
**而是**：严格使用预定义模板

**原因**：
- 保持结构一致
- 降低认知负担
- 便于长期维护
- 防止知识库失控

### 4. 持续迭代

**不要**：追求一次性完美
**而是**：
- 允许 draft 状态
- 渐进式完善
- 定期回顾更新

**原因**：
- 理解是动态的
- 降低启动门槛
- 保持知识库活力

## 与导师讨论的启发

**核心观点**：
真正的竞争力来自判断力、决策力和方法论，而非知识堆积。

**实践方法**：
- 每个项目结束后强制复盘
- 记录"如果重来会怎么做"
- 提炼可复用的判断框架
- 建立个人方法库

**避免陷阱**：
- 不要成为"资料收集者"
- 不要追求完整性
- 不要害怕记录失败

## 三层系统的设计逻辑

### 工作层（Obsidian）
**职责**：快速记录，低摩擦
**特点**：
- 允许混乱
- 允许不完整
- 允许情绪化

### 产出层（Knowledge Base）
**职责**：结构化沉淀，高质量
**特点**：
- 强制结构
- 强制思考
- 强制判断

### 展示层（HEP Home）
**职责**：精炼展示，对外价值
**特点**：
- 成熟内容
- 教学价值
- 可公开讨论

**流动方向**：
- 工作层 → 产出层：周末提炼
- 产出层 → 展示层：选择性转换
- 展示层 → 工作层：外部反馈

## 成功标准

知识库是否成功，看这些指标：

1. **能否快速进入新课题**
   - 打开 Knowledge Map 就能理解领域全景
   - 30 分钟内掌握核心问题和方法

2. **能否深化理解**
   - Concept Note 帮助打透概念
   - Feynman Note 测试理解深度

3. **能否复用经验**
   - Decision 记录避免重复错误
   - Method Note 快速调用工具

4. **能否产生新洞察**
   - Agent 提供多角度审视
   - 链接网络激发新想法

## 反模式

**避免这些做法**：

❌ 大量摘抄论文
✅ 提炼核心洞察

❌ 完整的知识体系
✅ 问题导向的知识网络

❌ 追求完美的笔记
✅ 快速记录，持续迭代

❌ 孤立的知识点
✅ 链接的知识网络

❌ 只记录成功
✅ 失败和教训同样重要
